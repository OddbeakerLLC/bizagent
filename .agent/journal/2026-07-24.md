## CP launch ack + outbox safety net

- CP posts deterministic `status`/`launch-ack` ("PTL on it…") into the console conversation immediately on hub spawn when pending inbox has `conversation_id` — before CLI boot. One ack per spawn; real hub replies (and hard failures) supersede it.

- UI styles `status` / `launch-ack` / `error` messages; tests cover ack, supersede, promote, fail, real-outbox no-op.
- Files: `conversations.js`, `hub-turn-safety.js` (new), `dispatcher.js`, `server.js`, `public/app.js`, `styles.css`, `tests/test-control-plane.sh`.

## control-plane.sh lost PID after restart

- Root cause: `scripts/control-plane.sh` only trusted `.bizagent/control-plane.pid` written by its own `nohup` start. systemd user unit, bare `node … serve`, or any restart that left the process up without refreshing the pidfile made status/stop/restart report "not running" while the server was still live (operator had to kill the node PID by hand).
- Fix (`edf0ea5`):
  1. Shell discovers live PIDs via `/proc` cmdline (`bizagent-control-plane.js serve --hub <this hub>`), refreshes the pidfile on status, and prefers `systemctl --user stop/start` when the hub's unit is installed/active (avoids `Restart=on-failure` respawn after raw kill).
  2. Server writes/clears `.bizagent/control-plane.pid` itself on start/exit so systemd-started instances stay trackable.
  3. Regression test: start bare serve → drop pidfile → status finds PID → stop kills process.
- Pushed public main `edf0ea5`. Applied to live hub: synced `scripts/control-plane.sh` + `control-plane/server.js`; restarted via new script (now under `bizagent-control-plane-bizagent-5fec1774.service`, :8787 HTTP 200). Verified status still works after deleting the pidfile.

Challenge: two launch paths (nohup wrapper vs systemd) with only a launcher-owned pidfile.
Lesson: the long-lived process must own its pidfile, and the wrapper must also discover by cmdline/unit — never pidfile alone.
